# パフォーマンステストの計画

機能テスト（`.\mvnw.cmd test` / `npm test`）とは別物である。毎回は回さず、**任意のタイミング**で実行する。

関連: [テストの考え方](./testing.md)（正しさ。E2E なし）、[N+1](./n-plus-one.md)、[ログ](./logging.md)（`duration_ms`）、起動は `backend` で `.\mvnw.cmd -Dmaven.test.skip=true spring-boot:run`

---

## なぜ毎回回さないか

負荷テストは時間がかかる。SQLite に大量の投稿を入れ、画像ファイルも増える。普段の H2 単体テストや Vitest（jsdom）に混ぜると、品質チェックが遅くなり、手元の `data/tripdiary.db` を壊す。

| いまの品質チェック | 何を見るか | 実行 |
|--------------------|------------|------|
| `backend` で `.\mvnw.cmd test` | 正しさ（H2。本番 SQLite に書かない） | いつも |
| `frontend` で `npm test` | 画面コンポーネント（jsdom。実ブラウザではない） | いつも |
| この資料の性能 | 遅さ・件数・描画・後始末 | **任意** |

jsdom では実スクロール・画像デコード・30秒ポーリング・Network の本数は測れない。課題の「E2E なし」は毎回の自動実行を指す。ブラウザ計測は `npm test` にも gitignore 済みの `frontend/e2e/` にも載せない。置き場は `perf/`（k6 のスクリプト）と、画面操作用の Playwright 設定である。

---

## ツール選定（JUnit や Vitest ではない理由）

いま入っているのは **正しさのライブラリ** である。負荷用ではない。

| いま使っているもの | 役割 | 性能に使わない理由 |
|--------------------|------|--------------------|
| JUnit 5 + Spring Boot Test（`*ApiTest`、H2） | 401/403、境界値、SQL の枝 | ほぼ直列。同時利用者を表さない。DB も本番の SQLite ではない。`.\mvnw.cmd test` に混ぜると毎回重い |
| MockMvc / `@WebMvcTest` | HTTP の契約 | プロセス内。Tomcat のスレッドや Hikari（pool size 1）の待ちは出ない |
| Mockito | 分岐のホワイトボックス | 時間を測る対象がモックになる |
| Vitest + Testing Library（jsdom） | 画面の表示と入力 | 実ブラウザではない。スクロールも画像も 30秒取り直しの体感も出ない |

「1回呼んで `assertThat(elapsed).isLessThan(200)`」も性能テストにはしない。回数が足りず P95 にならず、CI がマシンの忙しさで落ちる。

### 誰が「使う人」「メンテする人」か

SNS の利用者（タイムラインを読む人）は k6 も Gatling も触らない。ここで言う利用者は **シナリオを書いて回す人** と、あとから直す人である。

- 書く人: このリポジトリの開発者（Java と TypeScript の両方）
- 読む人: 授業のレビュー、将来の自分、同じ課題を引き継ぐ人
- 困ったとき: 検索・事例・質問が当たるコミュニティ

「バックエンドが Java だから負荷ツールも Java」は、書く瞬間の都合である。メンテでは **事例が多く、言語がフロントと共有できる方** が勝つことが多い。

### 負荷ツールの差分（k6 / Gatling / ほか）

**k6**（ケイシックス。Grafana k6）は JavaScript でシナリオを書く CLI である。`k6 run script.js` で仮想ユーザーを出し、`http_req_duration` の P95 / P99 が標準で出る。2026年時点の公開リポジトリの星の目安は k6 が約 3万、Gatling が約 7千（コミュニティ規模の代理指標。星＝利用者そのものではない）。開発者向けの HTTP 負荷では、いま最もよく名前が出る部類である。実行エンジンは Go の単一バイナリで、Maven には載せない。Grafana Cloud や Datadog には繋がない（課題はファイル確認まで）。

**Gatling**（ギャトリング。機関銃の Gatling。ギャザリング／ガソリンではない）は JVM 上の負荷ツールである。シナリオは Java。`mvnw -Pperf gatling:test` で任意実行でき、HTML レポートが厚い。Java だけの現場や、Maven に閉じたいチーム向き。コミュニティは k6 より小さい。

| | k6（この計画で API 層に使う） | Gatling | JMeter | JMH | Locust |
|--|-------------------------------|---------|--------|-----|--------|
| 言語 | JavaScript（frontend と同じ系統） | Java（backend と同じ） | GUI + XML | Java（メソッド単位） | Python |
| 実行 | `k6 run`（別インストール。`test` には混ざらない） | `mvnw -Pperf gatling:test` | GUI または CLI | `mvn` だがマイクロベンチ | `locust` |
| コミュニティ（目安） | 大きい。事例・質問が多い | JVM 現場に残る。全体では k6 より小さい | 企業導入の歴史は長い。新規のコードベースでは重い | 別用途 | Python 現場 |
| P95 | 標準出力に出る | HTML レポート | 出る | ナノ秒の分布。HTTP 物語ではない | 出る |
| この SNS との相性 | JWT → 一覧 → `before*` / `after*` を短く書ける | 同じシナリオを Java で書ける | シナリオ XML が重い | bcrypt や JWT 解析の机上計測向き | スタックが違う |
| ブラウザの描画 | browser モジュールはあるが、この SPA には Playwright | 不得意 | WebDriver サンプラは重い | 無い | 無い |

JMeter は「入っている会社」は今でも多い。ただし計画が XML で差分が見にくく、この課題のページング（Bearer とカーソル）はコードの方が提出しやすい。JMH はメソッドのナノ秒用で、一覧 API の同時実行や画面の LCP は測れない。

### なぜ API 層は k6 か（Gatling から見直した）

最初の案は「backend が Java だから Gatling」だった。言語を揃える利点はある。ただし次を置くと、このリポジトリでは k6 の方がよい。

1. **メンテする人が調べやすい。** 詰まったときの検索・サンプル・質問は k6 の方が当たりやすい。一人で持っている課題提出リポジトリでは、これが実コストになる。
2. **書く人もフロントと共有できる。** 画面は TypeScript、ブラウザ計測は Playwright（JS/TS）。API 負荷だけ Java の Gatling にすると、`perf/` が二つの言語になる。k6 なら性能まわりは JS に寄る。アプリ本体の Java は変えない。
3. **既存の JUnit に混ざらない。** k6 はそもそも `.\mvnw.cmd test` の外。任意実行の要求を、プロファイル無しで満たす。
4. **数字の意味は Gatling と同じ。** P50 / P95 / P99 はツールの宣伝ではなく、並べた応答時間のパーセント点である。

残る欠点は **k6 バイナリを Windows に入れる** ことである。普段の起動（`mvnw` / `npm`）には含めない。性能を回すときだけ入れる（例: `winget install k6`）。バージョンは資料にピンする。クラウド課金（Grafana Cloud k6）は使わない。

Gatling を選ぶ方がよいのは、チームが Java のみで、Maven 以外を禁止されている場合である。この作品は Java API と React 画面の両方があるので、その条件には当たらない。

k6 の browser モジュールで画面まで一本化しない。JWT が `sessionStorage` にあり、無限スクロールと 30秒取り直しがある。操作は Playwright、同時実行の P95 は k6、と分ける。

## P50 / P95 / P99 とは何か

応答時間を **速い順に並べたとき、何パーセント目の値か** を示す。単位は普通ミリ秒。k6 の `http_req_duration` の `p(95)` / `p(99)` がこれである。

平均（mean）だけ見ると、大半は速いのに少数の遅いリクエストが隠れる（あるいは逆に、少数の極端に遅い値で平均だけが悪く見える）。パーセント点は「利用者の何割が、この時間以内に終わったか」を直接言う。

### 並べ方

同じ API を 100 回呼んだとする。かかった時間を短い順に並べる。

```text
 1番目（最速） …  12ms
50番目         …  40ms   ← P50（中央値。半分はこれ以下）
95番目         … 120ms   ← P95
99番目         … 400ms   ← P99
100番目（最遅）… 2100ms  ← 最大値。タイムアウトやGCの一発
```

| 表記 | 意味 | この数字より遅かった割合 |
|------|------|--------------------------|
| **P50**（median） | ちょうど真ん中 | 50% |
| **P95** | 95番目 | 5%（100回なら 5回） |
| **P99** | 99番目 | 1%（100回なら 1回） |

「P95 が 120ms」は、**95% のリクエストは 120ms 以内**、残りの 5% はそれより遅かった、という意味である。P95 自体が「5% 遅い」わけではない。

サンプルが 100 より少ないと、P99 はほぼ最大値と同じになる。**件数がないとパーセント点は使えない。**

### 平均との違い（このアプリの例）

`GET /api/posts` を 100 回。99 回は 40ms、1 回だけ 2000ms（画像ディスクや SQLite のロック）。

| 指標 | 値 | 読み方 |
|------|-----|--------|
| 平均 | 約 60ms | 「だいたい速い」に見える |
| P50 | 40ms | 半分の利用者は 40ms |
| P95 | 40ms 付近 | ほとんどは速い |
| P99 | 2000ms | 100回に1回、2秒待たされる |

タイムラインは無限スクロールと約30秒の取り直しで **同じ API を何度も叩く**。100回に1回の遅さが、スクロールの途中で一度出る、という感じになる。平均 60ms だけ報告すると、その一発は消える。

### このアプリで何の P95 を見るか

エンドポイントごとに別の数字にする。ログインはパスワードのハッシュ（bcrypt）で意図的に重い。一覧と同じしきい値にしない。

| 対象 | 目安（自分の PC の相対値） | 理由 |
|------|------------------------------|------|
| `GET /api/posts`（limit=20、投稿が十分ある） | P95 を主指標。例: 200ms 以内 | 最も頻繁。コメント件数は同じ SELECT のサブクエリ |
| `GET /api/posts/{id}/comments` | P95 | 詳細を開いたときだけ。親1件なので N+1 ではない |
| `POST /api/login` | P95 は一覧より遅くてよい | ハッシュ計算。VU（同時仮想ユーザー）は少なめ |
| `POST /api/posts`（画像なし） | P95。同時書き込みは抑える | SQLite は書き込みがほぼ直列。`hikari.maximum-pool-size` は **1** |

ログの `duration_ms`（[logging.md](./logging.md)）は **1リクエストの実測** である。k6 の P95 は、同じ endpoint の `duration_ms` をたくさん集めて並べた結果、と考えてよい。Datadog は入れない。ファイルと k6 の要約を見比べる。

P99 は「ごく稀な遅さ」用。手元の短い試験ではブレが大きいので、提出の説明は **P95 を主、P99 と最大値は参考** にする。

### ブラウザではパーセント点を無理に出さない

P95 は **同じ種類の計測がたくさんあるとき** の話である。

| 層 | サンプル | 使う数字 |
|----|----------|----------|
| API 負荷（k6） | 同じ `GET /api/posts` を数百〜数千 | P50 / P95 / P99 |
| ブラウザ（Playwright 1〜3タブ） | ログイン1回、スクロール数ページ | **その回の実測**（何msでカードが出たか）。3回の値を P95 と呼ばない |
| 公開ページの Lighthouse | `/login` `/signup` を数回 | LCP / CLS / INP（Web Vitals）。ページロード1回の「遅かった描画」であり、API の P95 とは別物 |

フロントでパーセント点が欲しくなったら、k6 側で API のリクエスト数を増やす。Chromium を数百起動して P95 を出すのは、この課題の SQLite 構成には向かない。

## 2層（API とブラウザ）

体感の遅さは **ブラウザ → Vite:5173 → API:8080** に出る。バックエンドだけだと、スクロールで画面が固まる・30秒取り直しで位置が飛ぶ・カードごとにコメント API を打っていないか、が分からない。

| 層 | ツール | 見ること |
|----|--------|----------|
| A. API | k6 | サーバの P95、SQLite、SQL の件数 |
| B. ブラウザ | Playwright（Chromium） | 描画、無限スクロール、静かな取り直し、Network の本数 |

k6 の browser モジュールで画面まで一本化しない。この画面は JWT を `sessionStorage` に置き、IntersectionObserver と 30秒間隔がある。操作の安定は Playwright、同時実行の数字は k6、と分ける。

### 層A（API）のシナリオ

専用 DB に投稿を十分入れてから、起動中の 8080 へ当てる。仮想ユーザーは読み取り中心で少なめ（目安 5〜10）。書き込み同時はさらに抑える。

1. ログインしてトークンを取る（セットアップ。この時間は一覧の P95 に混ぜない）
2. `GET /api/posts?tab=all&limit=20` を繰り返す（ホットパス）
3. `beforeCreatedAt` / `beforeId` で続きを読む（無限スクロール相当）
4. `afterCreatedAt` / `afterId` で差分（静かな取り直し相当）
5. 任意: コメント一覧、画像なし投稿。画像ありと 5MB 境界は回数を絞る

ログインの負荷はシナリオを分ける（bcrypt で CPU が先に飽和する）。

### 層B（ブラウザ）のシナリオ

5173 と 8080 の両方を、perf 用の DB・画像ディレクトリで起動する。基本は **1ブラウザ**。同時タブは最大 3 程度。

| ID | 操作 | 見るもの |
|----|------|----------|
| B1 | `/login` → ログイン → 先頭カード | カード表示までの時間。`GET /api/posts` は 1本。コメント API がカード枚数分ないこと（画面側の N+1） |
| B2 | 下へ送り 3ページ（20×3） | `before*` が数回。スクロール中の長いタスク |
| B3 | 画像付きが混ざる | サムネデコード、CLS |
| B4 | 開いたまま 30秒超（目安 35秒） | `after*` が1回。スクロール位置と入力中本文が消えない。失敗してもエラーバーを出さない |
| B5 | コメントの多い投稿を開く | `getPost` と `listComments` の並列。一覧の表示完了 |
| B6（任意） | 小さい画像で投稿 | `setInputFiles` で input に載せる。OS のファイルダイアログは使わない |

公開の `/login` `/signup` だけ、任意で Lighthouse を足してよい。ログイン後は `noindex` なので、検索向け速度の話は公開2画面で足りる。

画像の OS ダイアログは自動化しない（[next-lesson.md](./next-lesson.md) の DevTools 注意と同じ）。

## データは本番 DB に書かない

機能テストが H2 を使うのと同じ理由で、性能も **普段使う SQLite を汚さない。**

すでに `application.yml` がある。

- `DB_PATH` … 既定 `./data/tripdiary.db`
- `UPLOAD_DIR` … 既定 `./uploads`

性能用は別パスにする。例:

```text
DB_PATH=./data/tripdiary-perf.db
UPLOAD_DIR=./uploads-perf
```

シードでユーザー・投稿・コメント・小さめの画像を入れる。`@yamada` など授業用アカウントの日常データは触らない。k6 が投稿やコメントを足しても、消す対象は perf 用ディレクトリだけになる。

Windows では、Spring Boot が開いたまま SQLite ファイルを消すと失敗する。**先にプロセスを止めてから消す。** WAL を使っていると `timeline-perf.db-wal` / `.db-shm` も残るので、同じ名前の派生ファイルも消す。

## テスト後のクリーンアップ

性能ランの成果物は「計測の証拠」と「捨ててよいゴミ」に分ける。DB とアップロードは **毎回捨てる。** 要約（P95 の数字）は残してよいが Git には入れない。

### 捨てるもの（必須）

| 対象 | 理由 |
|------|------|
| `data/tripdiary-perf.db` と `-wal` / `-shm` | シード＋負荷で増えたユーザー・投稿・コメント |
| `uploads-perf/` 配下のファイル | 投稿画像。ローカル保存のまま残すとディスクだけ増える |
| Playwright の trace / video / screenshot | 失敗調査用。残すなら `perf/results/` に限る |
| k6 の生出力を `perf/results/` に置いた場合 | 再実行で上書きしてよい |

`DELETE FROM posts` のような部分削除はしない。別ファイルごと消す方が、授業用 DB を誤って空にする事故が起きない。

### 残してよいもの（任意・Git に入れない）

| 対象 | 理由 |
|------|------|
| その回の k6 要約（P50/P95/P99 の数行） | 提出や前後比較 |
| ブラウザ1回の「カード表示 800ms」などのメモ | パーセント点ではない実測 |
| `backend/logs/` の JSON | `duration_ms` の突合。**自動では消さない**（普段のログ確認と場所が同じため） |

ログを消したいときは、性能の後始末とは別に、確認が終わってから手で消す。パスワード・トークンはログに出さない、は性能時も同じ。

### 手順（毎回この順）

1. 計測を終える（k6 / Playwright）
2. 必要な要約だけ `perf/results/` へ残す（残す場合）
3. **8080 の Spring Boot を止める**（5173 も止めてよい）
4. `timeline-perf.db`（と `-wal` / `-shm`）を削除する
5. `uploads-perf/` を削除する（空ディレクトリごと）
6. Playwright / k6 の一時ファイルを削除する（要約を残すなら `perf/results` 以外）
7. 普段の起動に戻すときは `DB_PATH` も `UPLOAD_DIR` も付けない（既定の `tripdiary.db` と `uploads/`）

ブラウザの `sessionStorage`（JWT）はコンテキスト終了で消える。追加のクリーンアップは不要。

誤って既定の `data/tripdiary.db` に負荷をかけてしまった場合は、**スクリプトで消さない。** 授業用アカウントが消える。バックアップが無ければ、その DB は手で判断する。

### Git に入れない

`.gitignore` に性能用の DB・画像・結果を足す。`frontend/e2e/` は従来どおり入れない。`.env` / `*.db` / `backend/target/` も入れない（既存ルール）。

## 実行の形（実装時）

```text
# いつも（機能。性能は走らない）
backend> .\mvnw.cmd test
frontend> npm test

# 任意（性能）
DB_PATH と UPLOAD_DIR を perf 用にして 8080 を起動
必要なら 5173 も起動
シード
k6 run perf/k6/timeline.js              # 層A。P95 を見る（mvnw test には載せない）
Playwright …                            # 層B。実測と Network 本数
後始末（上の手順 3〜6）
```

回すタイミング: 一覧 SQL を変えたとき、無限スクロールや30秒取り直しを触ったとき、投稿・コメントが増えたあと、提出前の一度。

やらないこと: 毎回のテストに乗せる、1000ブラウザ、WebSocket 負荷（使っていない）、S3 / 常時サーバ、既定 DB の自動削除、画像ダイアログの自動操作。
